# Architecture

## Current state (v5b, defended)

### Model

- Base: `Qwen/Qwen2.5-Coder-7B-Instruct` (7.61B params, 28 layers, 131k context)
- Adapter: LoRA on attention + MLP, r=16, alpha=32, 40M trainable params
- Training: 3 epochs, lr=1.5e-4 cosine, fp16, batch=1 with grad_accum=8

### Data

- Source: CVEFixes (real CVE fix commits from open-source repos)
- Train: 800 vulnerable + 800 safe = 1600 examples (balanced 50/50)
- Train answer template generated by DeepSeek-Chat-v3 as teacher (structured Type/Cause/VerificationSteps/Fix)
- Eval: 100 hold-out from CVEFixes (70 vuln + 30 safe), zero overlap with train

### Inference

- Greedy decoding, max_new_tokens=600
- Prompt format: chat template with system + user, structured output expected
- Calibration via threshold sweep on first-token logprobs (`p_vuln = P("Type") / (P("Type") + P("Verdict"))`)
- Best in-domain: threshold 0.40 -> F1 = 0.859

### Performance summary

|---|---|---|

## Next state (v8 triage)

### Task redefinition

Instead of "code -> vuln or safe", the v8 task is:

> Given a code snippet **plus an existing SAST finding** (tool, claimed CWE, severity, line range), decide whether the finding is a **true positive** or a **false positive**, and explain why.

This shifts us out of competing with Snyk/Semgrep as a scanner, and into competing as a **triage layer on top of them**. The pain (91% false-positive rate, alert fatigue) is much more directly addressed.

### Data plan

- Primary source: SastBench (arXiv 2601.02941, Jan 2026). Real CVEs as true positives, filtered SAST tool findings as approximate false positives.
- Augmentation: run Semgrep on fixed CVEFixes commits to get explicit false positives in the same projects.
- Distillation: use GPT-4o + Claude as teachers for the `Reasoning:` and `SuggestedFix:` fields.
- **Split by project, not by commit.** This is the hard lesson from v7lite (see HISTORY.md). Random split inflated apparent OOD performance by 2x.

### Model plan

- Stay on Qwen2.5-Coder-7B initially. Scale to 14B only after proving 7B has hit a capacity ceiling on triage (not before).
- LoRA r is a free parameter to tune: v7lite_r8 (r=8) beat r=16 on OOD, but triage may want more capacity for structured output.
- Default 2 epochs (lesson from v7lite: 3 epochs on 4k pairs caused memorization).
- Calibration the same way: threshold sweep on first-token logprobs of "TRUE_POSITIVE" vs "FALSE_POSITIVE".

### Two-stage option

Inspired by Datadog (Bits AI) and the LLM-as-FP-filter literature (arxiv 2506.10322):

1. Stage 1: predict TP/FP directly (our v8 above).
2. Stage 2: re-prompt the same model with `"Confirm the prediction. List concrete reasons the finding is real."` This adds ~2x inference cost but on OWASP Benchmark has shown FP rate drop from 92% to 6.3%.

We will implement both, A/B them, and ship the cheaper one if quality is comparable.

### Why not just go to 14B

Two reasons.

1. **Plateau is not capacity-bound.** Our v7lite (4079 pairs, larger train, balanced) underperformed v5b (1377 pairs) on in-domain (F1 0.78 vs 0.86). More data did not help, and v7lite_r8 (smaller LoRA) beat v7lite (larger LoRA) on OOD. The bottleneck is methodology (project leakage, narrow input context, no teacher distillation), not parameter count.

2. **14B without methodology fixes will just memorize harder.** LoRA r=8 was a regularization win. Going to 14B increases capacity 2x, which is the opposite direction.

We will revisit 14B **after** v8 triage is implemented and only if 7B caps out.

## Inference and serving (post-research)

Out of scope until v8 has clear metrics. Sketch:

- vLLM with continuous batching for throughput
- One L40S pod handles ~50 mid-sized repos at PR-comment latency (3-5 sec budget)
- Cold start: 30 sec on a warm pod, ~3 min from scratch
- Quantization: int8 with bitsandbytes for the enterprise on-prem flavor (fits on 24 GB)
