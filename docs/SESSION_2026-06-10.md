## End-of-day update

### What actually happened

The day's optimistic plan met reality. v8 trained successfully in 68 minutes
but eval returned **BA=0.510 on triage_100** — exactly random. Investigation
showed two compounding problems:

1. **The source data was wrong for the task.** v5b/v7lite "safe" samples were
   independent code from different CVEs, not post-fix versions of the
   vulnerable samples. Only 20 of 707 CVEs in v5b had both vuln and safe
   representations, and even those were not paired by file path. The triage
   task collapsed into detection.

2. **The FP reasoning was a single template.** All 1431 FP training examples
   used the same 279-character template "This code does not contain a CWE-X
   vulnerability. Either ...". The TP examples had rich varied reasoning from
   the original CVE Cause/Fix fields. The model learned the stylistic
   discriminator, not the semantic difference.

A check on the underlying logprobs confirmed the depth of the failure: the gap
between p_TP on real TPs and p_TP on real FPs was 0.007 (we need 0.05+ for any
calibration signal). The model has no internal signal at all.

### Late-day pivot: D2A dataset

A competitive landscape report received from the user at the end of the day
explicitly recommends the **D2A dataset (arxiv 2102.07995)** as the correct
methodological source for triage-style training. D2A is built on differential
analysis: for every bug-fix commit it stores both the pre-fix and post-fix
versions of the same code. This is exactly what we need.

Plan for tomorrow:

1. Pull D2A from https://github.com/IBM/D2A
2. Inspect schema, write prepare_d2a_triage.py
3. Build v8.2 training data from real pre/post pairs (project-stratified)
4. Retrain v8.2 (~$0.75 + 1.5 h on A6000)
5. Eval on triage_100 + full 573-case test
6. If BA ≥ 0.65 -> Sprint 2 (SARIF + evidence packet)
